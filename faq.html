General

About virtual-com.

What is virtual-com?

A Windows driver that creates virtual serial ports. Each port has a normal COM end that any serial application can open, and a private host end that your own software opens to supply and receive the data. It comes with a .NET library and a command-line tool for creating and managing ports.

Why is it a user-mode driver?

Two reasons: signing and safety. New kernel-mode drivers need Microsoft's signature to load with Secure Boot on. Since April 2026, Windows 11 24H2 and later have also stopped trusting the older cross-signed kernel drivers many free serial tools relied on. A user-mode (UMDF) driver has no kernel code, so it only needs a normal code-signing certificate on its package. And if it misbehaves, Windows restarts its driver host instead of the whole machine stopping.

How is it different from com0com and other null-modem emulators?

Those create two COM ports wired back to back, as kernel drivers. virtual-com creates one COM port and gives the other end to your program through a private interface, as a user-mode driver. So it suits software that wants to sit behind a port, rather than connecting two existing applications to each other.

Which versions of Windows does it support?

It's designed for Windows 10 version 1809 and later, and Windows 11, on 64-bit x86 PCs. It has been tested on Windows 11 25H2. ARM64 and Windows in S mode aren't supported, because those require Microsoft-signed (WHQL) driver packages.

Is it ready for production?

Not yet. It passes its behaviour test suite, but releases aren't yet signed with a publicly trusted certificate, and it hasn't been widely tested with third-party applications. Treat current builds as previews.

Can I use it commercially, or ship it with my product?

Yes. It's licensed under the Microsoft Public License (MS-PL), which allows commercial use and redistribution. If you distribute source, it must stay under MS-PL; if you distribute binaries, your licence terms must comply with MS-PL. Keep the copyright and attribution notices. Parts of the driver are adapted from Microsoft's MS-PL VirtualSerial2 sample.

Using ports

Day-to-day behaviour.

Can I choose the COM number?

Yes: vcomctl create COM20, or VirtualComDevices.Create("COM20"). The number is claimed in Windows' COM name database so no other device is given it. Pick a number nothing else uses, including USB adapters that happen to be unplugged.

How many ports can I create?

Each port is its own device, and the driver has no fixed limit. The practical limit is the COM numbers available; the tools accept COM1 to COM256.

Do the baud rate, parity and stop bits matter?

No. The application can set anything; the settings are stored, reported back to it and to the host, and never change the data. Data moves as fast as both ends read and write. If the far side really needs those settings, for example a device behind a network bridge, the host can read them and pass them on.

Is any data changed?

No. Bytes arrive unchanged and in order. All 8 bits are passed even if the application selects 7 data bits, where a hardware port would drop the top bit.

What happens when nothing is attached to the host end?

The application can still open the port. CTS, DSR and DCD are low, like an unplugged cable, and anything it writes is discarded. When a host attaches, the lines rise and data flows.

Can two applications open the same port?

No. Like a hardware serial port, each end accepts one open handle at a time; a second open fails with "Access is denied".

Is hardware or XON/XOFF flow control supported?

The settings are accepted and stored but not enforced. Flow control between the two ends comes from the buffers: a writer waits when the 64 KB buffer to the other end is full.

Which serial libraries and programs work with it?

Anything that uses the standard Win32 serial API should work. .NET's System.IO.Ports is covered by the test suite, including its DataReceived and PinChanged events. Others, such as terminal programs and pySerial, haven't been systematically tested yet. See the serial reference for exact behaviour.

Bridge app

The bridge app.

What is the VCNS Virtual COM Bridge?

A tray application, included in the repository, that gives serial software a COM port leading to a device's TCP port. You add a profile for each device and start it from the tray when you need it. See the bridge page.

How does NovaStar Proxy relate to it?

NovaStar Proxy is an edition of the bridge for NovaStar LED controllers: the same application with NovaLCT wording, port 5200 as the default, and a reminder to pause Zabbix polling before connecting. Improvements to the bridge reach every edition.

Will it reconnect if the link drops?

No, by design. Many such devices accept one session at a time, and an automatic reconnect could take that session from a monitoring system or a colleague without anyone choosing to. The bridge tells you the link dropped; you start it again when it suits.

What does "Port in use" mean?

The device accepted the connection and closed it straight away, or before sending anything. That's how single-session devices turn away a second client. Something else holds the session; stop or pause it and start again.

Can it expose a real COM port on the network instead?

Not yet. That's server mode, which is planned: real COM ports, such as USB-attached devices, each listening on their own TCP port.

Can I make an edition for my own product?

Yes. An edition is a small executable that passes its name, folders and wording to the shared application; the MS-PL licence allows it. See building a bridge edition.

Installation and signing

Installing and trusting the driver.

Does it work with Secure Boot and Memory Integrity on?

Yes. It was installed and tested with Secure Boot on and test signing off. Memory Integrity (HVCI) governs kernel-mode code; virtual-com's driver runs in user mode.

Why does Windows show Code 52, or "can't verify the digital signature"?

Windows doesn't trust the certificate the package was signed with. Current builds are signed with a test certificate. Import it into the machine's Trusted Root and Trusted Publishers stores, as the user guide explains, or wait for a production-signed release.

Do I need administrator rights?

Only to install the driver package and to create or remove ports. Opening either end of an existing port works as a standard user.

Does it need test-signing mode, or Secure Boot turned off?

No. Neither is needed, and neither is recommended.

How do I remove it completely?

Remove the ports with vcomctl remove, delete the driver package with pnputil /delete-driver, and remove any test certificate you trusted. The user guide has the exact steps.

Can I sign my own builds?

Yes. Any code-signing certificate that chains to a trusted root works for a user-mode driver package. build\Sign-Package.ps1 does the signing; see Build & sign.

Development

Building on it.

How do I write the host side?

In .NET, call VirtualComHost.Open("COM20") and use its Stream. Reads return as soon as the application has written something. The developer guide has echo and TCP bridge examples.

Can I use it from C, C++, Python or another language?

Yes. Find the port's host interface (GUID_DEVINTERFACE_VCOM_HOST), open it with CreateFile, and use ReadFile, WriteFile and two documented DeviceIoControl codes. See the native interface. From Python, pywin32 can do the same.

How does my host know what the application set?

GetState(), or IOCTL_VCOM_GET_PORT_STATE, returns: whether the application has the port open, its DTR, RTS and break state, baud rate, data bits, parity, stop bits, and the bytes waiting in each direction.

Why does a host read never return zero bytes?

So that a read loop is simple: zero would normally mean "end of stream". A read waits until data arrives. To stop waiting, cancel it or close the host end.

Can I run the tests in CI?

Yes. A Windows build agent can trust a throwaway test certificate, install the test-signed driver and run tests against a real port. The repository's GitHub Actions workflow, being added shortly, does exactly that on GitHub's hosted Windows runners; see Continuous integration.

virtual-com · Build & sign

Build it, sign it, ship it.

The driver builds with the standard C++ toolset and a Windows Driver Kit fetched from NuGet. There's no WDK installer and no Visual Studio WDK extension, so the same build runs on a laptop and on GitHub's hosted runners.

Prerequisites

Install the tools once.

winget install --id Microsoft.VisualStudio.2022.BuildTools --override "--passive --wait --norestart --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended --add Microsoft.VisualStudio.Component.VC.Runtimes.x86.x64.Spectre"
winget install --id Microsoft.DotNet.SDK.10
winget install --id Microsoft.NuGet

The Spectre-mitigated libraries are the easily missed part: the driver is built with Spectre mitigation on.

Build

Build the driver, library and tools.

git clone https://github.com/vcns/virtual-com.git
cd virtual-com
nuget restore packages.config -PackagesDirectory packages
msbuild driver\vcnsvcom.vcxproj -p:Configuration=Release -p:Platform=x64
dotnet build VirtualCom.slnx -c Release

The driver build compiles vcnsvcom.dll at warning level 4 with warnings as errors, Control Flow Guard, CET compatibility and the static C runtime, so there's no Visual C++ redistributable to install. It then assembles the package in out\Release\package:

  • vcnsvcom.dll, the driver;
  • vcnsvcom.inf, stamped with date, version and UMDF version;
  • vcnsvcom.cat, the catalog, still unsigned at this point.

The version comes from VersionPrefix in Directory.Build.props, plus a fourth part: CI's run number, or 0 for a local build. So a local build of 1.0.0 is 1.0.0.0, and each CI build is higher than the one before, which Windows takes as an upgrade. The DLL, the INF and the programs all carry it. Override it with -p:BuildNumber=…, or set the package version outright with -p:DriverVersion=1.2.3.4.

Why not the WDK's own project type?

Microsoft's driver project templates need full Visual Studio with the WDK extension. A user-mode driver is an ordinary DLL linked against the WDF stub library, so build/Umdf.props builds it with the standard v143 toolset and the defines the WDK applies. The only dependencies are Build Tools and the NuGet kits.

Signing

Sign the package.

Windows installs a driver package only if its catalog is signed by a certificate it trusts. A user-mode driver doesn't need Microsoft's signature: any code-signing certificate that chains to a trusted root will do, with an optional time stamp so the signature outlives the certificate. That covers 64-bit Windows 10 and 11. ARM64, S mode and Windows Update need Microsoft's signature, which is planned in Microsoft signing.

build\Sign-Package.ps1 -Thumbprint <certificate thumbprint>

The script signs the DLL, regenerates the catalog so it covers the signed DLL, and signs the catalog. All signatures use SHA-256 and an RFC 3161 time stamp; pass -TimestampUrl '' to skip the time stamp.

Development

A self-signed certificate:

New-SelfSignedCertificate -Type CodeSigningCert `
  -Subject 'CN=VCNS Virtual COM (test signing)' `
  -CertStoreLocation Cert:\CurrentUser\My

Trust it only on test machines, as described in the user guide.

Releases

Signed in CI with the Production environment's certificate (see Releases). For now that's the CI test certificate. With a publicly trusted VCNS Tech Ltd certificate, nothing needs importing, but Windows still asks an administrator to confirm the publisher the first time, and standard users can't install. Only Microsoft's signature avoids that prompt; see Microsoft signing.

Your own builds

MS-PL lets you ship your own builds. Sign them with your organisation's certificate, such as Azure Artifact Signing or an OV code-signing certificate, and they'll show your name as publisher.

Bridge

Build the bridge.

The bridge engine embeds the driver package so the app can install the driver itself. It looks for a signed package in out\Release\package, so build and sign the driver first. To use a package from elsewhere, pass its folder:

dotnet build src\vcombridge -p:VirtualComPackageDir=D:\signed\package\

To publish a single self-contained executable, with no .NET runtime needed on the target PC:

dotnet publish src\vcombridge -p:PublishProfile=win-x64     # -> out\publish\vcombridge\vcombridge.exe

build\Publish-Programs.ps1 -Thumbprint <certificate thumbprint> publishes both the bridge and vcomctl this way and signs them, as CI does.

Without a package, the bridge still builds and can use existing ports and com0com, but it can't create VCNS ports. Branded editions such as NovaStar Proxy build the same way from their own repositories, with virtual-com as a submodule.

Testing

Run the tests.

The tests exercise a real installed port through System.IO.Ports. First sign the package with your test certificate and export the certificate for the install script:

$cert = Get-ChildItem Cert:\CurrentUser\My | Where-Object Subject -eq 'CN=VCNS Virtual COM (test signing)'
build\Sign-Package.ps1 -Thumbprint $cert.Thumbprint
New-Item -ItemType Directory out\test-signing -Force | Out-Null
Export-Certificate -Cert $cert -FilePath out\test-signing\vcom-test-signing.cer

Then install and test:

# administrator PowerShell: trust the test certificate, install, create COM20
scripts\Install-TestPort.ps1 -Port COM20

# any prompt
$env:VCOM_TEST_PORT = 'COM20'
dotnet test tests\Vcns.VirtualCom.Tests
dotnet test tests\Vcns.VirtualCom.Bridge.Tests

The bridge tests cover configuration, port allocation and the bridge itself, using a simulated device and serial port over loopback. With VCOM_TEST_PORT set, they also run end-to-end tests through the real driver: a System.IO.Ports client, the bridge, TCP and a simulated device. Without VCOM_TEST_PORT, the port tests and end-to-end tests are skipped. scripts\Uninstall-Test.ps1 removes the ports, the package and the certificate again.

CI

Continuous integration.

The GitHub Actions workflow, .github/workflows/build.yml, runs on a hosted Windows Server 2025 runner for every pull request and every push to main. A pull request that changes only the website or Markdown files skips the Windows build but still reports its Build and test check, so the check can be required; pushes of such changes to main don't start it. It:

  1. restores the NuGet kits, cached between runs;
  2. builds the driver, versioned with the run number, checks the package against Microsoft's signing rules (build\Test-Package.ps1) and signs it;
  3. builds the library, tool, bridge and tests, with the signed package embedded;
  4. trusts the signing certificate on the runner;
  5. installs the driver, creates COM20, and runs the driver and bridge test suites.

Pushes to main also publish the bridge and vcomctl as signed single executables and upload three artefacts: driver-package-test-signed, with the package and vcomctl.exe; vcombridge-test-build; and driver-symbols, the driver's PDB for reading crash dumps. The first two have vcom-test-signing.cer next to their files. Pull requests upload nothing, so only take test builds from runs on main. When the build, install or tests fail, the install log and setupapi.dev.log are uploaded as install-logs.

Because the runner is a throwaway virtual machine, trusting the certificate there carries no risk.

Signing certificates are kept in two GitHub environments rather than in the repository's secrets:

  • Development holds the CI test certificate. Only main can use it, so a pull request can't reach the key, even by changing the workflow. Every build from main is signed with it, so a PC that trusts it once can install later test builds too. The signatures are time-stamped, so they stay valid after the certificate expires. Pull requests are signed with a throwaway certificate instead.
  • Production holds the release certificate. Only main and v* tags can use it, and each use needs a maintainer's approval. Until VCNS Tech Ltd has a publicly trusted certificate, it holds a copy of the CI test certificate, so releases are test-signed.

CI has a certificate of its own rather than your development certificate: its key lives in GitHub, so it shouldn't be one your PCs already trust for your own builds. A repository admin sets up both environments, a five-year CI certificate, private vulnerability reporting, immutable releases and the rules for main with:

scripts\Set-GitHubEnvironments.ps1                      # PowerShell 7, with gh logged in

The key never touches the disk, and the local copy is deleted once GitHub has it. Until the script has been run, builds from main are signed with a throwaway certificate and the run shows a warning, and releases fail. Runs also warn 60 days before the certificate expires; run the script again to replace it.

The rules for main: a commit reaches it only once GitHub Actions' Build and test check has passed on it, so every change goes through a pull request, and its history can't be rewritten. They apply to admins too.

Releases

Make a release.

  1. Set the version in VersionPrefix in Directory.Build.props, through a pull request like any other change.
  2. Once it's merged, tag the merge commit and push the tag: git tag v1.2.3 <commit> then git push origin v1.2.3.
  3. The workflow's Build, test and draft the release job waits for a maintainer to approve it, under the Production environment.
  4. It checks that the tag matches the version and is on main, then builds, tests and signs exactly as for main, with the Production certificate, and creates a draft GitHub release.
  5. Read the draft and choose Publish release. Nothing is public until then.

Releases are immutable: once published, a release's files and tag can't change, and its tag name can't be used again, even if the release is deleted. Its title and notes can still be edited. To fix a release's files, release a new version.

The release has vcombridge.exe, vcomctl.exe, the driver package and the driver's symbols as zip files, and SHA256SUMS.txt. If it's test-signed, it also has vcom-test-signing.cer, and its notes say how to trust it. The notes then list the pull requests merged since the last release.

The programs are self-contained, so each release carries the .NET runtime it was built with. Make a new release after a .NET security update. Dependabot opens pull requests for the workflow's actions weekly and for NuGet packages monthly.

Contributing

Issues and pull requests.

Bug reports, compatibility reports ("application X does Y on a virtual-com port") and pull requests are welcome on GitHub. For a compatibility problem, please include the application and version, what it does on a hardware port, and what it does on the virtual one. Contributions are accepted under the project's MS-PL licence.

Please don't report security problems in a public issue. Report them privately from the repository's Security tab, as SECURITY.md describes.

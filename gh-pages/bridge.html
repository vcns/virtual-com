virtual-com · Bridge app

A COM port that leads to the network.

The VCNS Virtual COM Bridge is a ready-made host for virtual-com ports. It gives serial software a COM port on this PC that leads to a device's TCP port, so vendor tools that only speak COM can manage networked devices unchanged. In server mode it works the other way round, sharing this PC's real COM ports on TCP ports.

At a glance

  • Tray application for Windows 10 1809+ and Windows 11, x64
  • Client mode: a virtual COM port per device, connected to its TCP port when you ask
  • Server mode: real COM ports shared on TCP ports by a Windows service
  • Protects devices that accept a single session
  • Bytes forwarded unchanged, as soon as they arrive
  • Administrator approval only for port, service and firewall changes
  • Branded editions, such as NovaStar Proxy

Overview

What it does.

Many devices now sit on a network but still speak their original serial protocol on a raw TCP port, while the software that configures them still expects a COM port. In client mode, the bridge creates a virtual COM port for each device and, when you start it, connects that port to the device's TCP port. Server mode, further down, is the reverse.

Profiles

Each profile maps one virtual COM port to one TCP endpoint. Several devices get several ports, numbered above every COM port already used or reserved on the PC.

On demand

Nothing connects at start-up. You start a profile from the tray menu, and it stays connected until you disconnect it or the link fails. It never reconnects by itself.

A real "cable"

While a profile isn't connected, its port looks like a serial port with nothing plugged in. CTS, DSR and DCD rise only once the device has accepted the session.

Getting started

Setting up.

No published release yet

Build the bridge from source as described in Build & sign. Until production signing is in place, builds carry a test-signed driver, so first trust the test certificate on the PC.

  1. Copy vcombridge.exe to a folder such as C:\Program Files\VCNS Virtual COM Bridge and run it. A connector icon appears in the notification area; if it's hidden, click the ^ arrow by the clock.
  2. Right-click the icon and choose Settings → GUI…, or double-click the icon. The line near the top should mention VCNS virtual COM (included).
  3. Choose Add. A row appears with a COM port already chosen. Type the device's address in Target Server and its TCP port in Target Port.
  4. Choose Save. When asked "Create virtual port COM9?", choose Create and approve the Windows prompt. The first time, this also installs the driver.
  5. When the row says Virtual port ready, right-click the icon and choose Start → COM9 → address:port. The icon turns green when the device has accepted the session.
  6. Open COM9 in your serial application and work as usual. Choose COM9 — Connected → Disconnect when you've finished.

Illustrative values. Starting the program a second time opens the running copy's Settings window.

Rules checked when you save

  • Every profile needs a valid server, a port from 1 to 65535, and a COM port from COM1 to COM256.
  • Each COM port belongs to one profile, and each endpoint to one COM port.
  • A COM port that belongs to other hardware is refused.
  • A connected profile can't be removed or have its connection changed until you disconnect it. Saving never interrupts a connection.
  • Nothing is written if any check fails, and the file is replaced atomically, so a failed save never damages the previous configuration.

Safety

Single-session safety.

Many serial-over-TCP devices serve one client at a time and drop any other, while monitoring systems poll them on the same port. The bridge never takes a session another client holds.

RiskSafeguard
Two profiles reaching the same deviceRefused at start. The lock matches the configured name and every resolved address.
Reconnecting before the device has released the last sessionRelease interval (default 2 s) after every disconnect.
Another client already holds the sessionDetected when the device closes the new connection straight away, or before sending anything. Reported as Port in use; the other session is left alone.
Competing with other clients in the backgroundNo automatic connection at start-up and no automatic reconnection.
The application talking before the link is upModem lines stay low until the device has accepted the session.

Files

Files and logs.

Configuration
%APPDATA%\VcnsVirtualComBridge\config.json, human-readable JSON. The previous version is kept as config.json.bak. It contains no passwords.
Logs
%LOCALAPPDATA%\VcnsVirtualComBridge\logs\vcom-bridge-YYYYMMDD.log, one per day, kept for 30 days.
What's logged
Start-up and exit; each connection's COM port, target and TCP endpoints; the outcome and reason; the application's port settings when the connection starts; and bytes forwarded each way.
Byte-level logging
Off by default. Switch on Log forwarded data in hex only while investigating a problem.

Other editions use their own folder and log names; NovaStar Proxy, for example, uses NovaStarProxy and novastar-proxy-YYYYMMDD.log.

Server mode

Share a real COM port on the network.

Server mode is the reverse of client mode. A COM port on this PC, typically a USB-attached device, listens on its own TCP port, and whatever connects to that port talks to the device. Clients can be another PC running the bridge in client mode, a monitoring system, or any program that opens a raw TCP connection.

How a shared port behaves

A shared port behaves like a single-session serial device server, the same way devices with a built-in serial-over-TCP port do. A client that works with one works with the other, and monitoring checks can be reused.

AspectBehaviour
ProtocolRaw TCP: no handshake, banner or Telnet negotiation. Bytes pass unchanged in both directions.
ClientsOne at a time. Any other client is accepted and closed straight away, and the current session isn't disturbed. Client mode reports this as Port in use.
COM portOpened when a client connects and closed when it leaves, so other software on this PC can use it in between. DTR and RTS are raised while it's open.
Line settingsFixed per port (baud rate, data bits, parity, stop bits, flow control). Raw TCP clients have no way to change them.
Allowed clientsOnly listed addresses and ranges are served; others are closed at once. The firewall rule is limited to the same addresses.
Dead connectionsDetected within about 30 seconds by TCP keep-alive, freeing the port for the next client.
Device unpluggedThe client is disconnected. The next client to connect gets the device again once it's back.
ChangesApplied as soon as they're saved. Only the ports you changed restart; clients on other ports stay connected.

Server mode

Sharing a COM port.

  1. Put the program in C:\Program Files\VCNS Virtual COM Bridge and run it from there. Server mode runs it as a Windows service, so it refuses to run from a folder that standard users can change.
  2. Plug in the device and check its COM port in Device Manager.
  3. Open Settings → GUI…, choose the Server ports tab and tick Share COM ports on the network.
  4. Choose Add. The row picks the next COM port that's present, a TCP port (the base plus the COM number), this PC's main network address, and that address's subnet as the allowed clients.
  5. Adjust Allowed Clients to the PCs or ranges that should connect, and set Baud, Format and Flow Control to match the device.
  6. Choose Save and approve the Windows prompt. The bridge installs and starts its service and adds the firewall rules, then shows "Server settings applied".
  7. Check the row's Status says Listening. From a client PC, Test-NetConnection <this PC> -Port 4003 should succeed.

Illustrative values. The tray menu's Server entry shows the same status, each port's latest event (such as a client being turned away), and a shortcut to the server log.

Transparency

What server mode changes on the PC.

Settings
%ProgramData%\VcnsVirtualComBridge\server.json. Only administrators can change it; everyone can read it. The service ignores the file if anyone other than administrators owns it.
Service
VCNS Virtual COM Bridge server (VcnsVirtualComBridgeServer). Runs the same program with --service as the low-privilege LocalService account, starts automatically, and restarts after a failure.
Service files
%ProgramData%\VcnsVirtualComBridge\service: the server log (logs\vcom-bridge-server-YYYYMMDD.log, 30 days) and status.json. The only folder the service can write to.
Firewall
Inbound rules named VCNS Virtual COM Bridge server, one per shared port, limited to its TCP port, listen address, allowed clients and this program.

Unticking Share COM ports on the network and saving removes the service and the firewall rules. The settings file stays, so ticking it again restores your rows.

Monitoring

Monitoring shared ports.

A shared port looks the same on the network as a device with its own single-session TCP port. A monitoring system that already polls such devices over TCP, for example a Zabbix template, a script or an agent check, can poll <host>:<TCP port> the same way. Usually only the host address and port change.

  • One session at a time. While monitoring polls, other clients get Port in use, exactly as they would from the device itself. Pause or schedule polling around configuration work.
  • Each poll opens the COM port. Every TCP connection opens the COM port and raises DTR and RTS; disconnecting closes it. That suits most devices, but one that resets when DTR rises would reset on every poll.
  • Allow the monitoring server. Add its address (or the monitoring proxy's) to Allowed Clients.
  • Watch the service too. Monitor the VcnsVirtualComBridgeServer Windows service, or simply the TCP port, so you know if sharing stops.

Editions

Branded editions.

An edition is the same application with its own name, folders, defaults and wording, for a particular kind of device. Behaviour is identical in every edition. The engine (Vcns.VirtualCom.Bridge) and the tray app (Vcns.VirtualCom.Desktop) are shared; an edition is a small executable that passes a BridgeEdition to BridgeApp.Run.

using Vcns.VirtualCom.Bridge;
using Vcns.VirtualCom.Desktop;

internal static class Program
{
    [STAThread]
    private static int Main(string[] args) => BridgeApp.Run(new BridgeEdition
    {
        ProductName = "Line 2 Bridge",
        DataFolderName = "Line2Bridge",
        LogFilePrefix = "line2-bridge",
        SerialApplication = "the PLC software",
        DeviceNoun = "PLC",
        DefaultTargetPort = 4001,
        OtherClientExample = "the SCADA poller",
    }, args);
}

Security

Security.

  • Client mode makes outgoing connections only, to the endpoints you configure, when you start them. It opens no listening sockets and doesn't change the firewall.
  • Server mode does listen, so it's off until you turn it on. Each shared port listens on the address you choose, serves only its allowed clients, and has a firewall rule limited to them.
  • The TCP link carries the device's own protocol, unencrypted and usually without authentication: anyone allowed to connect to a shared port can drive the device. Keep allowed clients tight, and use a management network or a VPN.
  • The server runs as the low-privilege LocalService account, from a program in Program Files, with settings only administrators can change.
  • No credentials are stored, and there's no telemetry or update check.
  • The tray app runs as a normal user. Creating or removing ports and changing server mode run in a short-lived elevated copy of the program, one Windows prompt per change.

virtual-com · Use cases

When software only speaks COM.

Plenty of Windows software can only reach its device through a serial port: vendor configuration tools, PLC and instrument software, older line-of-business applications. virtual-com lets your own code stand where the cable used to be, without changing that software.

  • Serial software to a networked device
  • Device simulators and emulators
  • Automated testing of serial applications
  • Traffic logging and protocol analysis

Pattern 1

Bridge serial software to a networked device.

Many devices now sit on a network but still speak their original serial protocol, sometimes over a raw TCP port. The configuration software, however, still expects a COM port. A small host application can open the port's host end and a TCP connection, then copy bytes between them. The vendor's software talks to COM20 as if the device were plugged in locally.

Why virtual-com suits this

  • The host decides when the "cable" is connected. It can keep CTS, DSR and DCD low until the TCP session is established, so the application doesn't start talking too early.
  • The host can read the application's chosen baud rate and line settings, and log them or pass them on to a device that cares.
  • Only one application can open the COM end, which matches devices that accept a single session.
  • No kernel driver to get past IT security reviews or Secure Boot.

Ready-made: the bridge

You may not need to write this yourself. The repository's VCNS Virtual COM Bridge does exactly this, with single-session protection, on-demand connections and clear error reporting. Its NovaStar Proxy edition lets NovaLCT manage NovaStar LED controllers over the network.

Pattern 2

Simulate a device that isn't there.

Write a host application that answers like the real instrument, modem, GPS receiver or controller would. Developers and support staff can then use the real client software against a simulated device: to reproduce a customer's problem, demonstrate features, or train staff without hardware.

  • Play back captured responses, or generate them from a model of the device.
  • Simulate a cable being pulled, by dropping the modem lines or closing the host end.
  • Inject delays or partial responses to see how the client copes with a slow or faulty device.

Pattern 3

Test serial applications automatically.

Because the host end is just another handle, a test framework can drive it. Test your application's real serial code against scripted exchanges, including time-outs, event waits, purges and line changes, without serial hardware or loopback cables.

  • Runs on ordinary Windows build agents: trust the test certificate on the agent, install the driver, and run the tests against a real port, as virtual-com's own test suite does.
  • Deterministic: the test controls exactly what the application receives and when.
  • Inspect what the application configured (baud rate, DTR, RTS, break) through the host's state query.

Pattern 4

Log and analyse serial traffic.

Put a host application in the middle: it relays to the real device, through a physical port or the network, and records every byte in both directions with timestamps. This helps when reverse-engineering an undocumented protocol, auditing what a vendor tool sends to production equipment, or tracking down an intermittent fault.

Pattern 5

Gateways and gradual modernisation.

Keep a legacy application unchanged while its backend moves on. The host end can translate between the application's serial dialogue and a modern service: an HTTP API, MQTT, WebSocket or a database. The old software keeps working while the infrastructure behind it is replaced.

Limits

When not to use it.

Two existing applications

To connect two off-the-shelf serial applications directly to each other, you need two COM ports wired back to back. virtual-com gives you one COM port and a programmable host end, so you would write a small relay between two ports.

Physical timing

There is no physical line. Data moves as fast as both ends read and write, not at the configured baud rate, and break or parity errors are not simulated on the data path.

ARM64 or S mode

Those editions of Windows require Microsoft-signed (WHQL) driver packages. virtual-com currently targets x64.

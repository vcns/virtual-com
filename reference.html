virtual-com · Serial reference

What the COM end supports.

How the driver handles each serial request an application can make, for developers who need to know whether their serial software will behave the same as on a hardware port.

Rule of thumb

  • Settings: accepted, stored and reported, but they don't change the data
  • Time-outs, events, status and purge: implemented as Windows' serial driver behaves
  • Line errors and baud-rate timing: not simulated

Compatibility

Time-outs

Read and write time-outs.

Reads follow the COMMTIMEOUTS rules Windows documents for serial ports. A read that times out still returns any bytes it collected; ReadFile succeeds with fewer bytes than requested.

IntervalTotal multiplierTotal constantBehaviour
MAXDWORD00Return immediately with whatever is buffered, even nothing.
MAXDWORDMAXDWORD1 … MAXDWORD−1Return as soon as at least one byte is available; give up after the constant with nothing. .NET SerialPort uses this for its ReadTimeout.
000No time-outs: wait until the whole buffer is filled.
nmcComplete when the buffer is full, when m × length + c ms have passed (if either is non-zero), or when n ms pass between bytes (once at least one byte has arrived).

Writes complete when every byte has been passed to the host's buffer. If the buffer stays full, the write total time-out (WriteTotalTimeoutMultiplier × length + WriteTotalTimeoutConstant) applies. Time-outs are checked against the system tick count, so expect up to about 16 ms of extra delay.

Events

Wait events.

EventRaised when
EV_RXCHARThe host writes data to the application.
EV_RXFLAGThat data contains the event character set with SetCommState.
EV_RX80FULLThe buffer to the application is at least 80% full.
EV_TXEMPTYEverything the application wrote has been read by the host (or discarded).
EV_CTS, EV_DSR, EV_RLSD, EV_RINGThe corresponding line changes: the host end opens or closes, or the host sets the lines.
EV_BREAK, EV_ERRNever: there are no line errors or incoming breaks.

Events that happen while no wait is pending are remembered and returned by the next WaitCommEvent, as Windows' serial driver does.

Lines

Modem lines.

CTS, DSR, DCD (RLSD)
Raised when the host end opens and dropped when it closes. The host can set them at any time.
RI (ring)
Low unless the host raises it.
DTR, RTS
Set by the application and reported to the host. They don't affect CTS or DSR, and there is no hardware flow control loop.
Flow control settings
RTS/CTS, DTR/DSR and XON/XOFF settings are accepted and stored but not enforced. Instead, full buffers make the writer wait.

Properties

Reported properties.

GetCommProperties reports an RS-232 port with:

  • maximum baud rate "user-defined", so any value is accepted;
  • all standard baud rates;
  • 5–8 data bits; 1, 1.5 and 2 stop bits; all parity modes;
  • DTR/DSR, RTS/CTS and XON/XOFF capabilities;
  • total and interval time-outs;
  • current queue sizes of 65,536 bytes each way.

Testing

Tested clients.

The test suite drives the COM end with .NET's System.IO.Ports.SerialPort, which uses the Win32 calls above. It covers:

  • enumeration;
  • typical 115200 8N1 settings with DTR and RTS;
  • exclusive open;
  • simultaneous transfers of 256 KB each way, and 600 KB bursts larger than the buffer;
  • read time-outs and first-byte returns;
  • modem lines with PinChanged, BytesToRead, DiscardInBuffer and DataReceived;
  • discard with no host attached;
  • cancelling a pending read on close.

Other clients that use the standard Win32 serial API, such as terminal programs or pySerial, should behave the same but haven't been systematically tested yet. Please report any differences.

Limits

Limits.

  • x64 only; Windows 10 1809 (UMDF 2.25) or later.
  • 64 KB buffer in each direction, per port.
  • Data is never masked to the configured data bits; all 8 bits pass through.
  • No parity, framing or overrun errors; no simulated baud-rate timing.
  • Each end accepts one open handle at a time.
